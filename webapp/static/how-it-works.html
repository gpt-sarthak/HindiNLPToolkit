How the pipeline works

← back to the toolkit

01 What this tool does

Hindi is a verb-final language with fairly free word order before the verb: the phrases of राम ने सीता को किताब दी can appear in several orders and stay grammatical — yet speakers systematically prefer some orders over others. This toolkit studies why. It takes real, human-written sentences, generates the alternative orders of their preverbal phrases, and asks a set of cognitive and statistical predictors which order they find more natural — testing ideas like dependency length minimization (languages prefer orders that keep grammatically related words close together).

There are two ways to use it. In Sentence mode you type one Hindi sentence (plus, optionally, the sentence that came before it): the app parses it, permutes its preverbal constituents, scores every candidate order, and recommends the most natural one. In File mode you upload a corpus (.conllu or .txt): the app filters it, builds a reference-vs-variant pairs table for research or ML use, and can evaluate how accurately each predictor identifies the human-written order.

Everything below is computed on this server; nothing is sent elsewhere. Each step of the pipeline writes a downloadable artifact as soon as it finishes.

02 The pipeline

Four steps run for every job, then one of two endpoints depending on the input mode. Click a step to see how it is computed.

1 Parse text → dependency trees

Every sentence must become a dependency tree before anything else can happen:

  • .conllu uploads are read directly — they already contain gold dependency trees in CoNLL-U format, in either the Paninian (k1/k2…) or UD (nsubj/obj…) annotation scheme. The scheme dropdown must match the file; the two schemes share no labels and are never mixed.
  • .txt uploads and typed sentences are parsed with Stanza's Hindi pipeline, which always outputs UD — this is why Sentence mode fixes the scheme to UD.
  • In Sentence mode the optional context sentence is parsed separately. It is handed to context-aware scorers as "the preceding sentence" but is itself never filtered or permuted.
writes parsed.conllu (only when the input was plain text)
2 Filter keep only sentences whose order can be studied cleanly

Seven filters run in a fixed order; a sentence must pass all of them. The "Filter summary" card reports how many failed at each step.

  1. Interrogative — rejected if the sentence contains ?, a WQ tag, or an interrogative pronoun (PronType=Int). Interrogative word order follows its own rules.
  2. Negation — rejected on a NEG tag or Polarity=Neg; negation constrains order too.
  3. Empty nodes — rejected if the tree contains fractional token IDs (empty nodes like 1.1) that would break reordering.
  4. Non-projective dependencies — rejected if any dependency arcs cross; constituents can't be moved as clean blocks otherwise.
  5. Non-verbal root — the root must carry a tag the chosen preset accepts as the clause head: VERB/AUX/VM/VAUX under the Paninian preset, VERB/AUX/NOUN/ADJ/PROPN under UD (copular sentences root on the predicate nominal). This step also extracts the preverbal constituents — the units everything downstream permutes.
  6. Punctuation-attached constituent — rejected if a bare punctuation token hangs off the root as a constituent of its own.
  7. Too few preverbal constituents — rejected with fewer than 2 preverbal constituents, since no nontrivial reordering would exist.
writes passed_sentences.csv rejected_sentences.csv summary.json
3 Generate variants permute the preverbal constituents

Each surviving sentence's preverbal constituents are permuted — whole constituents move as blocks, the verb stays final. With 3 constituents that's 3! = 6 possible orders: the original plus up to 5 variants (capped by the max variants option).

The output is a surface-only pairs table — one row per (reference, variant) pair with the columns Sent_ID | Variant_ID | ML_Label | Reference_Sentence | Variant_Sentence and no scores yet. ML_Label is the flip signal (1 = reference listed first, 0 = flipped), alternating row by row for a 50/50 balance — see the Delta columns for why.

In File mode a grammar filter additionally drops reorderings whose adjacent dependency-label pairs never occur anywhere in the uploaded corpus — a cheap plausibility check. Sentence mode skips it (one sentence is too little evidence), so all permutations are kept.

writes variants.csv
4 Score every ticked scorer rates both orders

This step runs only if you ticked at least one scorer; with none ticked the pairs table stays surface-only and no Delta_* columns exist — which is what makes the Evaluate branch report "no predictors".

Each scorer you ticked appends its raw score for both orders of every pair as a column pair — e.g. LSTM_Reference / LSTM_Variant. These always keep their true roles: the reference column is always the human-written order.

Scorers that need the preceding sentence (information_status, adaptive_lstm) receive it from the corpus: in File mode, whatever sentence precedes it in your upload; in Sentence mode, your context box — and there, if you leave the box empty, those scorers are dropped from the run.

After all scorers have run, one central diff step computes every Delta_* column from ML_Label. No scorer computes its own difference, so every delta is oriented identically — the full rule is in the Delta columns below.

extends variants.csv
File mode · opt-in
5a Evaluate

With at least 200 pairs, a 10-fold cross-validated logistic regression tries to predict ML_Label from each Delta_* feature alone, and from all of them together. The report is out-of-fold accuracy against the 50% chance baseline, plus coefficient directions — the method of Ranjan & van Schijndel (2024). Details in Evaluation accuracy.

writes evaluation.json
Sentence mode · always
5b Recommend

Your original order and all its variants are ranked by combining the ticked scorers' raw scores — z-scored within the sentence, oriented so higher = more natural, and averaged with fitted weights. The winner becomes the "Recommended word order" card. Details in The recommendation score.

The same per-sentence winner is written as three columns (Recommended_Sentence, Recommended_Is_Reference, Recommended_Score) into variants.csv in both modes — so File mode gets a recommendation for every sentence in the corpus, right beside the scores.

writes recommendation.json variants.csv columns

03 The seven scorers

A scorer is a plugin that assigns each word order a number. Some are deterministic measurements of the parse tree; others are trained language models. The direction badge on each tile tells you how to read the raw number: for surprisal-style scores lower means the order is easier to process, while for likelihood-style scores higher does.

Dependency length Delta_DL

↓ lower = more natural

Measures how far apart grammatically related words sit. Each dependency arc contributes its length minus one (Gildea & Jaeger); the score is a 5-element vector [total_DL, last_DL, second_last_DL, last_len, second_last_len], and the delta uses total_DL. Shorter dependencies are easier to process — the core DLM prediction.

Deterministic — computed from the parse, no training.

Information status Delta_IS

↑ higher = more natural needs context

Checks whether given information (mentioned in the preceding sentence) comes before new information: +1 when the given phrase precedes the new one, −1 when new precedes given, 0 otherwise. Speakers prefer given-before-new.

Deterministic heuristic over the parse (Ranjan & van Schijndel 2024). File mode uses the preceding sentence of your upload; Sentence mode uses your context box, and the scorer is dropped if you leave it empty.

Constituency surprisal Delta_Surprisal

↓ lower = more natural

Incremental syntactic surprisal in bits: how surprised a probabilistic phrase-structure grammar is by each word as it reads the sentence left to right, summed over the sentence.

Berkeley hdtb_fresh PCFG + the Taru incremental parser; trained on the Hindi Dependency Treebank.

Trigram Delta_Trigram

↓ lower = more natural

Surprisal under a classic 3-gram language model: how unexpected each word is given the previous two, with backoff to shorter contexts for unseen sequences. A simple, purely word-sequence baseline.

NLTK maximum-likelihood 3-gram with 3-level backoff smoothing.

LSTM Delta_LSTM

↓ lower = more natural

Surprisal in nats under a recurrent neural language model — a stronger sequence model than the trigram, sensitive to longer-range patterns.

2-layer LSTM trained on Hindi Wikipedia.

Adaptive LSTM Delta_Adaptive

↓ lower = more natural needs context

The same LSTM after one quick learning step on the preceding sentence, so its expectations adapt to the local discourse before it scores the target (van Schijndel & Linzen 2018).

Adapts on the preceding sentence of your upload in File mode, or your context box in Sentence mode — where the scorer is dropped if you leave it empty.

Berkeley PCFG Delta_PCFG

↑ higher = more natural

Whole-sentence log-likelihood under a Berkeley constituency grammar — the odd one out: it is a probability, not a surprisal, so higher means more natural. Distinct from the constituency-surprisal scorer, which uses a different grammar and an incremental (word-by-word) computation.

Berkeley Parser, DS-PS grammar (13,282 HUTB trees).

04 The Delta columns

Every scorer stores its raw scores true-role: *_Reference is always the human-written order, *_Variant always the reordering. The Delta_* column is the score difference, oriented by ML_Label:

ML_LabelmeaningDelta_X =
1reference listed firstX_Reference − X_Variant
0pair flipped, variant firstX_Variant − X_Reference

Think of ML_Label as saying which order is "first" in the pair; Delta is always first minus second. Labels alternate 1/0 down the table, so exactly half the rows are reference-first. Why bother? A model trained to predict ML_Label from the deltas can't beat chance by always guessing "the reference is better" — it is forced to actually use the score difference. This is the standard pairwise ranking transform (Joachims 2002).

A worked example — the LSTM gives the reference 42.1 nats of surprisal and the variant 45.3 (the reference is easier):

ML_LabelLSTM_ReferenceLSTM_VariantDelta_LSTM
142.145.3−3.2
042.145.3+3.2

Same scores, opposite signs — and either way the model learns the same rule: the lower-surprisal side is the human-written order. Note the raw columns never flip; only the delta does.

05 Evaluation accuracy (File mode)

The "Ranking accuracy" card answers one question per predictor: if a model saw only this feature, how often would it pick the human-written order over a reordered variant? 50% is coin-flip chance; every point above it is real signal.

Method. The pairs table is split into 10 folds (fixed shuffle, so runs are reproducible). For each fold, a logistic regression is trained on the other nine to predict ML_Label from the Delta_* features (z-scored per fold) and tested on the held-out fold; the headline number pools accuracy over all held-out predictions. Each feature is evaluated alone, then all together as the combined row. The displayed coefficients come from a fit on all the data with effectively no regularization.

Reading the coefficients. Their sign should match each scorer's declared direction — negative for lower-is-better raw scores (dependency length, surprisals), positive for higher-is-better ones (information status, PCFG log-likelihood). When it does, the feature behaves as theory predicts.

Reference numbers on the full UD Hindi treebank (193,474 pairs): dependency length ≈ 61.7%, information status ≈ 51.3%, combined ≈ 62.6%. Small uploads give noisy accuracy — that is why evaluation requires at least 200 pairs (below the floor the card reports "insufficient pairs") and why serious numbers need a full corpus.

06 The recommendation score (Sentence mode)

Sentence mode always ends with a "Recommended word order" card: your original sentence and every generated variant, ranked. The combined score behind that ranking is built in five steps:

  1. Every candidate order gets each ticked scorer's raw score — read straight from the scoring step, nothing recomputed.
  2. Only scorers with a declared direction vote (all seven built-ins have one).
  3. Per scorer, the scores are z-scored across this sentence's candidates only, and the sign is flipped where needed so that higher always means more natural.
  4. A candidate's combined score is the weighted mean of those oriented z-scores, taken over the features that actually produced a number for it — a feature that fails to compute (a blank NaN cell, say when Java is unavailable for the PCFG scorers) drops out of that candidate's average rather than counting as zero. All seven built-ins carry a fitted weight: Delta_Trigram 1.882, Delta_Adaptive 1.822, Delta_LSTM 1.820, Delta_PCFG 0.896, Delta_Surprisal 0.872, Delta_DL 0.638, Delta_IS 0.306. So better-validated predictors get a louder vote, but a weight can never flip a scorer's declared direction.
  5. The highest combined score wins. Exact ties go to your original order.

Where the weights come from. Each is the strength of its feature in a standardized logistic regression, fitted offline and then fixed. Their provenance is mixed: Delta_DL comes from our own full-corpus fit on the bundled UD Hindi treebank (193,474 pairs); the other six from the Ranjan & van Schijndel research feature table (92,299 pairs), with Delta_Surprisal computed on those same sentences here.

Reading the number. The score is relative to this sentence's own candidate set: 0 is an average candidate, positive is better than average, negative worse. It is not comparable across sentences or runs — only the ranking within one card is meaningful.

In File mode. There is no card, but the same winning order is written per sentence into variants.csv as Recommended_Sentence / Recommended_Is_Reference / Recommended_Score — one recommendation per source sentence, repeated on each of its variant rows, so it scales to a whole corpus.
